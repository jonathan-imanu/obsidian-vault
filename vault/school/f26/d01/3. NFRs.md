# Non-functional Requirements

The architectural requirements present in an application. These are the requirements that enable the system to operate maintain and extend in quality. They can be broken down into two types:
1. *Operational:* Capabilities of the system in production
2. *Structural:* Qualities of the system itself

Determining the importance of an NFR is based on business / product / org. needs.
##### NFRs $\neq$ Architectural Characteristic **BUT** in CSCD01 NFRs = Architectural Characteristic 

### The Netflix Story

**August 2008**

Netflix operated primarily as a DVD subscription storefront and a logistics network across 50 states to mail DVDs directly to customers. They had scaled to support 9M customers.

The logistics network was supported by a centralized enterprise database server. Their current scale was achieved by updating the hardware that their central server ran on.

There were two problems:
1. A DB corruption issue stopped DVD shipments from going out for 3 full days
2. Netflix had recently launched the "Watch Now" feature which allowed users to stream titles over internet.

Netflix was doing **vertical scaling**.

# More on Scaling

**Software System**: A set of components that work together to deliver a set of behaviours.
**Datastore**: Anywhere in a software system where data is stored.
### CAP Theorem

Given a distributed datastore, we can only fulfill two of these three:

![[school/f26/d01/CAP.png]]\
- **Partition Tolerance**: System continues to operate even if some nodes fail during a network call.
- **Consistency:** Every read returns the most recent write or an error.
- **Availability:** every request to a non-failing node must result in a non-error response.

In reality, every system must be partition tolerant. Systems choose between consistency and availability.

Components in an architecture that require **state** (datastores) pose difficulties when it comes to scaling. There is no perfect option when it comes to scaling a state-reliant component. Every option comes with a tradeoff to either **availability** or **consistency**:

### Vertical Scaling

The simplest option. The state reliant component is a single-point of failure and a potential bottleneck in a system.
### Multi-Primary Architecture

**What?**

The DB replicas sync their data. An application will write and read to any DB replica and these replicas will sync with each other.
### One Primary DB and many Read Replicas

**What?**

App servers write to only one primary database. All other DB replicas are considered read-only. These *read replicas* will have their data synced with the primary DB.

Between these various options, we leave the question: **When does data actually sync?**
## Async vs. Sync Replication

### Sync.

Synchronous replication will wait for an ACK from the replica before completing the write. The replica will only return an ACK once all replicas confirm a write to disk.
- **Consistent but blocking writes will hamper availability**
### Async.

Asynchronous replication will return success immediately after a local primary write. The primary will commit locally and stream the changes to replicas asynchronously. The replicas will then apply these changes asynchronously. 
- **Highly available but may not be consistent** 
## Availability

Availability can be comprised from server failure or inevitable maintenance (both hardware and software).

Both the acceptable amount of availability and the methods of measuring it are business and needs dependent. 
- **SLA**: Service Level Agreement is the downtime allowed over some time period.
### 1. Time based Availability

$$\text{availability} = \frac{\text{uptime}}{\text{uptime + downtime}}$$

Calculating uptime can be done with periodic requests to some health check endpoint. But this is not perfect because this endpoint may not be a good heuristic on system health.

### 2. Aggregate Availability


$$\text{availability} = \frac{\text{successful requests}}{\text{total requests}}$$

We can use the load-balancer for this information.

## Performance

**Latency**: A measure of the response time to a request.

Improving latency can be done by improving data retrieval or the compute.
### Caching

Improve the performance of data retrieval and computation by either:
1. Retrieving from RAM instead of disk
2. Performing a computation in advance and retrieving the results rather than re-performing the computation
#### Read-Through Caching

Data is loaded into the cache on demand. Data read once will likely be read again soon.

**Pros**:
1. Good for frequently read data
2. The cache only contains data that has been recently read
**Cons**:
3. Cache misses can lead to DB spikes
4. Data can potentially be stale
#### Write-Through Caching

The write operation will write to database and cache, the cache is always up to date.

**Pros**:
1. Simple application logic
2. There is no risk of a stale cache
**Cons**:
3. Higher write latency
4. Risk of cache becoming a bottleneck
5. Writes populate cache even if they won't be read 
#### Hybrid Approach

Typically the best of both worlds but more complex.
## Structural Requirements

### Upgradability

How easy it is to upgrade the system. Challenges include:
1. API specification changes
2. Database schema changes
3. Data migrations

API backward compatibility is ensuring that consumers of the old version can continue to use the application even after a version upgrade.
#### Semantic Versioning 

`X.Y.Z`

- `X`: Major release that contains backward incompatible changes. `Y` & `Z` are reset to 0.
- `Y`: Minor release that is backward compatible that still has substantial new functionality. `Z` is reset to 0.
- `Z`: A patch release that has backward compatible bug fixes.

### Single vs. Multi-Tenants

Whether multiple users share the same underlying infrastructure.

**Single Tenant**: One user / organization maps to distinct infrastructure. Like healthcare, Superset, GitHub Enterprise.
- *Pros*: 
	- Private
	- Secure
	- User benefits associated with customizing hardware / infrastructure / interface
- *Cons*: 
	- Infrastructure costs and efforts scale linearly with user count

**Multi-Tenant**: Multiple users share the same underlying infrastructure. 
- *Pros*: 
	- Easier to setup from the perspective of the customer
- *Cons*: 
	- Riskier deployment
	- Hard to scale
#### The Noisy Neighbour Problem

*There can be friction as the result of sharing infrastructure*.

**Problem**: One tenant over-consumes shared CPU, memory, bandwidth and disk I/O. Can only be prevented using:
- Horizontal scaling 
- Application performance monitoring
- Per-tenant rate limiting
- Dedicate single-tenant instances
### Configurability

### Maintainability
