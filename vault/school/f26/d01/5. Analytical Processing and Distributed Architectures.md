# Operational vs Analytical Data

## Operation Data - Online Transaction Processing (OLTP)

Used for business purposes such as sales, transactions and inventory. This data is used day-to-day and ensures that the business runs smoothly. 
- **Usual form is 3NF - split into many tables, normalized database**
## Analytical Data: OLAP (Online Analytical Processing)

Data is used for BI and is not critical for operations but informs long term business strategy and decision making. This kind of data is typically used for:
- Predictive analytics
- Dashboarding
- Reporting

**Usual form is 1NF - denormalized, big wide tables**
## Why Make a Distinction?

You can run both on the same database, but operational and analytical queries have different workloads - *so separating them protects performance and allows each to be optimized.*

![[OLTPvsOLAP.png]]

> It is not wise to have a large analytical query consume resources from a production DB as it can potentially slow down user facing operations

**Recognizing this distinction it makes more sense to store analytical data in high-write, aggregate read databases.**
- There are typically "column-oriented" or "time-series" data stores or flat file data formats
- Optimized for fast writes and aggregated reads of event data
	- Column layout allows for concurrent writes and unique compression strategies
	- Automatically optimizes data on insert
- Usually has a SQL-like API but is not 1:1 with relational DBs

## ETL: Extract Transform Load

The process of going from operational to analytical data.

![[ETL.png]]

### Data Warehouse

*This analytical store can be referred to as a **Data Warehouse***. Data customers can then access this warehouse directly. 

**DW Pros**:
1. Simple interface for customers
2. Purpose built schemas
**DW Cons**:
3. No domain separation
4. Limited functionality
5. Lossy transformation
6. Double documentation for data (analytical vs operational)

![[MoreETLs.png]]
### Data Lake

A way of keeping data before we decide exactly how to use it. We avoid lossy transformations, the need to maintain 2 database schemas, etc.

**Pros**
- Data analysts get to interact with raw data
- Better suited for distributed architectures
**Cons**
- Sometimes difficult to understand operational relationships
- Data consumers would need to denormalize themselves

![[DataLake.png]]
### Data Lakehouse

![[DataLakehouse.png]]

Combines the best of both worlds. It can replace lake-and-warehouse setups but it may not always meet the needs of an organization. Many companies use both setups because:
1. their workloads differ and they may need the guarantees a separate warehouse would provider
2. they want independent systems

# Microservices vs Monoliths

**Microservices prefer duplication (using near duplicate logging libraries in two services) as opposed to coupling so that services can run independently from each other.**

Uber originally had two monoliths but had the following issues:
1. Availability risks
2. Expensive deployments (frequent rollbacks)
3. Poor separation of concerns
4. Too many dependencies with people/teams

They moved to a domain oriented microservice architecture.

Monoliths can be still be used to great success. Shopify uses a "*modular monolith*":
1. Better code organization
2. Isolating dependencies: Decoupling business domains from one-another. Disallow cross-component associations.
3. Enforcing boundaries: Build tooling to analyze codebase for violations.
