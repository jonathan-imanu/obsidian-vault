Within a monolithic application, attaining higher availability comes with a higher cost. A part of this are the following problems with *horizontally scaling monolithic applications*:
- Cannot scale features effectively
- Brittle codebase
- Technology Lock-In

**Service-oriented architecture**: Systems are organized into services that each provide a distinct business capability and communicate through a well-defined interface.
- Aims to reduce coupling at the service level. Any shared functionalities will have “duplicated code”.

# Message Queues

**A example use-case**: Receive results from the backend's backend. 

They enable asynchronous service to service communication. They have the following use cases:
- **Batching**: Handling 10 elements together instead of 1 at a time
- **Buffer**: Slow down processing for spiky workloads.

## Data Processing Architecture Styles

### Pipeline Architecture Style

Data point comes in, do some complicated logic, output is stored or returned.

![[PipelineArch.png]]
- One way of implementing this is with Apache Beam
- Common filters include `map` and `filter`

### Broker Topology - Domain Focused

A singular message queue that shows that events have occurred. An asynchronous version of the pipeline architecture style. 
- This async nature leads to a *fire and forget* pattern and makes it hard to determine:
	- if an job succeed 
	- determining where and why a job failed within the system

![[BrokerTopo.png]]
 
 **Pros**:
 - Loose coupling
 - Easy to extend - we can add subscribers to topics without changing publishers
 - Concurrent processing
**Cons**:
- Debugging can be challenging 
- Failure recovery will be complex
- Introduces a dependency on messaging
#### Mediator Topology 

Have a centralized event mediator that sends data to each of the event processors but expects data back.

![[MediatorTopo.png]]

**Pros**:
- Clearer workflow
- Similar to broker topology wrt. to event processors
**Cons**:
- The mediator is a single point of failure and a potential bottleneck for scaling
- Stronger coupling
## Trade Offs with a Distributed Architecture

1. Latency ($T$) is far larger with a remote access call from service to service than a call between two local components in memory:

$$T_{remote} >>> T_{local}$$
2. The network is not reliable. There is no response after request 
3. The network is not secure. Each service will need to be secured with its own auth policy. 
4. A distributed architecture does not imply or always result in losser coupling
