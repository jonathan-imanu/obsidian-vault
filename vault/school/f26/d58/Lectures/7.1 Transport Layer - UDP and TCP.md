Transport layer is communication between processes running on different hosts. It serves the application layer and encapsulates (and relies on) data from the network layer.

Transport protocols provide logical communication between application processes running on different hosts:
- **Sender**: Breaks application messages into segments then passes them to the network layer
- **Receiver**: Reassembles segments into messages and passes into application layer
## Multiplexing and Demultiplexing

**Multiplexing**: A methodology that allows the combining of multiple signals into one signal over a shared medium.

**Demultiplexing**: Taking data from one signal and delivering it to the correct recipient (port).

Every datagram has:
- source and destination IP addresses
- carries a transport layer segment
- source and destination port numbers

Hosts use IP address and port number to direct the segment to the appropriate segment.
# UDP: User Datagram Protocol

A no-frills extension of "best-effort" IP by adding port numbers to support (de)multiplexing. It is lightweight communication between process that avoids overheads associated with ordered, reliable delivery. 
- Messages are sent and received from a socket.

UDP has the following advantages:
1. There is finer control over what data is sent and when because UDP sends packets from data as soon as an application writes into the socket
2. There is no delay for connection establishment
3. No connection state so no allocation of buffers, parameters, sequence numbers, etc.

UDP is used for:
- Multimedia streaming
- Query protocols like DNS
 
 because the overheads of connection establishment and retransmission at transport layer are not worthwhile / overkill.

# TCP: Transport Control Protocol

TCP is *reliable, ordered, connection-oriented and a byte stream service*. It also providers flow and congestion control.
##### What do you mean by byte stream service?

It sends a stream of bytes rather than messages. 
- The sender writes bytes into a TCP connection and
- The receiver reads bytes out of the TCP connection.

TCP does not transmit individual bytes over the internet.
## TCP Segments

TCP on the source host buffers enough bytes from the sending process to fill a reasonably sized
packet and then sends this packet to its peer on the destination host.

TCP on the destination host then empties the contents of the packet into a receive buffer, and the receiving process reads from this buffer at its leisure.

The packets exchanged between TCP peers are called **segments**.

![[TCPSegments.png]]

**A segment is sent when**:
1. Segment is full
2. Segment is not full but times out
3. Segment is not full but pushed by an application

![[TCPIPPacket.png]]
> A IP Packet. The TCP segment is no more than Maximum Segment Size bytes. TCP Header is typically 20 bytes long. IP Packet is no more than Maximum Transmission Unit (MTU).

## TCP Headers

![[TCPHeader.png]]

The `Acknowledgment`, `SequenceNum`, and `AdvertisedWindow` fields are all involved in *TCP’s sliding window* algorithm.
- The `Acknowledgment` and `AdvertisedWindow` fields carry information about the flow of data going in the other direction.
- `SequenceNum` reps the sequence number for the first byte of data in a segment.

The `Checksum` field is used in exactly the same way as for UDP as is computed over the TCP header, TCP data and pseudoheader.
### Flags

`Flags` is a 6 bit field used to relay control information between TCP peers. Flag options include `SYN`, `FIN`, `RESET`, `PUSH`, `URG` and `ACK`.
- The `SYN` and `FIN` flags are used when establishing and terminating a TCP connection, respectively.
- The `ACK` flag is set any time the Acknowledgment field is valid, implying that the receiver should pay attention to it.
- The `URG` flag signifies that this segment contains urgent data. When this flag is set, the `UrgPtr` field indicates where the nonurgent data contained in this segment begins.
	- The urgent data is contained at the front of the segment body, up to and including a value of `UrgPtr` bytes into the segment.
- The `PUSH` flag signifies that the sender invoked the push operation, which indicates to the receiving side of TCP that it should notify the receiving process of this fact.
- The `RESET` flag signifies that the receiver has become confused, it received a segment it did not expect to receive—and so wants to abort the connection.
## TCP Three-Way Handshake

![[TCP3WayHandshake.png]]
1. Host A SYN will include the it's ISN within the sequence number field. The flags section will be marked with `SYN`
2. Host B SYN ACK will include it's ISN within the sequence number field and will contain `ISN from Host A + 1` in the `Acknowledgement` field. The flags section will include `SYN` and `ACK`
	1. **A can start sending data after receiving this packet**
3. Host A's ACK will contain it's ISN within the sequence number field and will contain `ISN from Host B + 1` in the `Acknowledgement` field.  The flags section will be marked with `ACK`.
	1. **B can start sending data after receiving this packet**
### What if the `SYN` packet gets lost?

After a default timeout of 3 - 6 seconds, the sender will retransmit the `SYN` packet if no `SYN-ACK` has arrived.
- If a user gets impatient during the timeout wait, an abort will be sent and a new `SYN` will be sent.
## TCP Connection Teardown

**FIN** means “I have finished sending.” Each direction closes separately:

1. A sends **FIN** after its remaining data.
2. B sends **ACK**. B can still send data (connection is **half-closed**).
3. B sends **FIN** when finished.
4. A sends **ACK**.

B can combine steps 2–3 into **FIN + ACK**.

- **EOF:** After reading all data preceding the FIN, the receiving application reads EOF.
- **Sequence numbers:** FIN consumes one; a pure ACK consumes none.
- **RST:** Aborts the connection immediately; remaining data may be lost.
- **TIME_WAIT:** The final ACK sender waits temporarily to acknowledge a retransmitted FIN.
## Reliable Data Transfer
#### What makes Reliable Data Transfer Hard?

1. Data can arrive in order but some bits can be corrupted.
	1. The receiver should detect the errors and request retransmission
2. Data can arrive in order but some bits can be missing or corrupted
	1. The receiver can detect errors but cannot **always** detect loss. 
	2. The sender will wait for an ACK and retransmit if no ACK arrives
### TCP Support for Reliable Delivery

1. **Checksum** to detect corrupted data at the receiver. Using checksums, receiver will know when to drop packets.
2. **Sequence numbers** are used to detect missing data and for putting the data back in order.
3. **Retransmission** is when the sender retransmits lost or corrupted data. There is a timeout based on estimates of round-trip time. Fast retransmit algorithm for rapid retransmission.
### Sequence Numbers 

A segment's sequence number is the number of its first data byte.
- Sequence numbers help TCP identify missing data, put data in order and recognize duplicates.

A receiver will send an ACK to the sender that reports the progress to the sender.

> ACK 1000 -> receiver has received all bytes through 1000

For ordinary data segments:

> `Next sequence number = current sequence number + number of data bytes`
#### Initial Sequence Number (ISN)

An old connection’s delayed packet might arrive after the same IP addresses and ports have been reused. Changing the **initial sequence number (ISN)** helps prevent that old data from being mistaken for new data.

The **three-way handshake exchanges each side’s ISN**. If A’s SYN uses sequence number `x`, B acknowledges it with `ACK = x + 1`: **SYN consumes one sequence number**.
### Retransmission

#### Automatic Repeat reQuest (ARQ)

1. Receiver sends acknowledgment (ACK) when it receives packet. 
2. Sender waits for ACK and timeouts if it does not arrive within some time period

![[TCPRetransmissionReasons.png]]

#### Determining how long to wait?

**Do it based on the RTT**

A sender can estimate this by watching the ACKs:
- Smooth estimate: keep a running average of the RTT
- EstimatedRTT = a * EstimatedRTT + (1 –a ) * SampleRTT
- Compute timeout: TimeOut = 2 * EstimatedRTT

`ACK` isn't an acknowledgement of a transmission but rather acknowledging receipt of data because of this, after retransmitting data, we cannot tell which copy caused the `ACK`.
- This can either cause RTTs that are too large or too small

**The simple solution is don't use samples unless they were only transmitting once.**
# TCP Sliding Window 

The retransmission approach associated with **Stop-Wait ARQ** is inefficient as only one TCP segment is "in-flight" at a time.

The sliding window process allows a larger amount of data "in-flight" by allowing the sender to get ahead (but not too far ahead) of the sender.

It serves the following purposes:
1. it guarantees the reliable delivery of data,
2. it ensures that data is delivered in order, and
3. it enforces flow control between the sender and the receiver.
### Sender

- **LastByteAcked:** last byte acknowledged by the receiver.
- **LastByteSent:** last byte transmitted.
- **LastByteWritten:** last byte the application placed in TCP’s send buffer.

$$
LastByteAcked \le LastByteSent \le LastByteWritten
$$

- **Sent but unacknowledged:** `LastByteSent − LastByteAcked`
- **Waiting to be sent:** `LastByteWritten − LastByteSent`

### Receiver

- **LastByteRead:** last byte consumed by the application.
- **NextByteExpected:** next missing byte needed for in-order delivery; the TCP ACK number.
- **LastByteRcvd:** highest-numbered byte received, possibly out of order.

$$
LastByteRead < NextByteExpected \le LastByteRcvd + 1
$$

If there are no gaps, `NextByteExpected = LastByteRcvd + 1`.
## Receiver Buffering

Using the `Advertised Window` field in the TCP header, the receiver can advertise the amount of data that can be sent without acknowledgement.
- The sender agrees not to exceed this amount.
## Fast Retransmission

Resend missing data before the timeout expires.

As we send data that hasn't been `ACK`'d, when we receive a third duplicate `ACK` from a receiver we can view this as a hint that the `nth` packet must have been lost and retransmit this data.

> Segment `N` may have been lost but that doesn't mean that segments `N + 1 - N + M` were
### When does this work best?

1. Long data transfers
2. High window size
3. Low bustiness in packet loss

This doesn't do too much for **Web Traffic** as most transfers are short (< 10 packets) so retransmission doesn't kick in as often.
## TCP Flow Control

Flow control prevents the sender from overflowing the receiver’s buffer.

### Receiver Buffer

$$
LastByteRcvd - LastByteRead \le MaxRcvBuffer
$$

The lecture calculates the advertised window using received, in-order bytes not yet read:

$$
AdvertisedWindow = MaxRcvBuffer - ((NextByteExpected - 1) - LastByteRead)
$$

### Sender Window

Unacknowledged data must fit within the advertised window:

$$
LastByteSent - LastByteAcked \le AdvertisedWindow
$$

**EffectiveWindow** is how many additional bytes the sender may send:

$$
EffectiveWindow = AdvertisedWindow - (LastByteSent - LastByteAcked)
$$

### Sender Buffer

TCP retains written data until it is acknowledged:

$$
LastByteWritten - LastByteAcked \le MaxSendBuffer
$$

If writing another **y bytes** would exceed this limit, TCP blocks the application until buffer space becomes available.
