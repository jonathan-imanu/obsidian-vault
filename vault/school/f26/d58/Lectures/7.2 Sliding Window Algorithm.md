## Expectations for Sliding Window

1. Reliable
2. Preserves order as each frame has a sequence number
3. Frame control 
	1. Receiver is able to throttle the sender to ensure that it is not overrun
## Sender Protocol

Sender assigns a sequence number denoted as `SeqNum` to each frame. We assume that it can grow infinitely large.

The sender maintains three variables
- **Sending Window Size (SWS)**: An upper bound on the number of outstanding (unacknowledged) frames that the sender can transmit
	- The sender has to be willing to buffer up to SWS frames
	-  Can be set to **BDP (Bandwidth Delay Product)**
- **Last Acknowledgement Received (LAR)**: Sequence number of the last acknowledgement received
- **Last Frame Sent (LFS)**: Sequence number of the last frame sent

> The sender maintains the invariant that `LFS - LAR <= SWS`.

When an acknowledgement arrives, the sender moves LAR to right and transmits another frames
- The sender associates a timer with each frame it transmits and retransmits the frame if the timer expires before the ACK is received
## Receiver Protocol

The receiver maintains three variables:
- **Receiving Window Size (RWS)**: An upper bound on the number of out-of-order frames that the receiver is willing to accept
	- This can be anything. Is either `1` or `SWS`
- **Largest Acceptable Frame (LAF)**: The sequence number of the largest acceptable frame
- **Last Frame Received (LFR)**: Sequence number of the last frame received

> The receiver maintains the invariant that `LAF - LFR <= RWS`

Upon receiving a frame with Sequence Number `SeqNum`:
- Discard the frame if `SeqNum <= LFR` or `SeqNum > LAF`
	- *For the latter case, we need to decide whether or not to `ACK`*

**`SeqNumToAck`**: Denotes the largest sequence number not yet acknowledged, such that all frames with sequence number less than or equal to `SeqNumToAck` have been received

The receiver acknowledges the receipt of `SeqNumToAck` even if high-numbered packets have been received. This acknowledgement is said to be cumulative.

The receiver then sets
- `LFR = SeqNumToAck`
and adjusts
- `LAF = LFR + RWS`

## Issues with Sliding Window Protocol

1. When timeout occurs, the amount of data in transit decreases since the sender is unable to advance its window.
2. When the packet loss occurs, this scheme is no longer keeping the pipe full
	1. The longer it takes to notice that a packet loss has occurred, the more severe the problem becomes

Some ways to fix this are:

1. **Negative Acknowledgement (NAK)**: Receiver will send a `NAK` for frame `M` (where `M < N` and `M` is a missing frame) when frame `N` arrives
2. **Additional Acknowledgement**: Receiver sends additional `ACK` for frame `M - 1` (where `M < N` and `M` is a missing frame) when frame `N` arrives
	1. This is used as a clue for frame loss
3. **Selective Acknowledgement**: Receiver will acknowledge exactly those frames it has received, rather than the highest number frames.
	1. This allows the sender to keep the pipe full at a higher complexity.
### Finite Sequence Numbers

The header field includes a finite sequence number so we must wrap around sequence numbers.

Sequence numbers wrap around and get reused. The receiver must distinguish **old retransmissions** from **new frames with the same number**.

Let:
- **N (MaxSeqNum):** number of available sequence numbers.
- **SWS:** maximum number of outstanding, unacknowledged frames.
- **RWS:** size of the receiver’s acceptance window.
### When RWS = 1

**SWS + 1 ≤ N** is sufficient.

The receiver accepts only the next expected frame, rejecting old duplicates.
- Stop-and-wait: SWS = 1, so two sequence numbers (0 and 1) suffice.
### When RWS = SWS

Equal windows must use **at most half the sequence-number space**:

$$
SWS < \frac{N + 1}{2}
$$

Example of failure with **N = 8, SWS = RWS = 7**:
1. Sender sends frames 0–6.
2. Receiver accepts them and moves its window to **7, 0–5**.
3. All ACKs are lost, so the sender retransmits old frames 0–6.
4. Old frames **0–5** fall inside the new window and may be mistaken for new data.

With **SWS = RWS = 4**, old frames **0–3** and the next window **4–7** do not overlap, avoiding this ambiguity
