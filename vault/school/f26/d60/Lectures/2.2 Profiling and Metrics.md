# Profiling

Dynamic program analysis that measures a performance metric. An evidence-based method to find performance problems.

## Tracing

Events happening during code execution are logged.
- Need to know what events you want logged.
- Depending on how it’s done, can slow down code.
- Depending on the tool, may be hard to interpret
## Sampling 

At periodic intervals, the state of the system is logged. This shows us where time is spent. 

**Benefits**:
- Allow us to get finer-grained (more detailed) information about where time is being spent
- Very low overhead
- No instrumentation
**Disadvantages**:
- Not a trace so does not tell us why the code was there
- Requires sufficiently long runtime to get enough sample

### Using `gprof` Sampler

When you compile include `-pg` to turn on profiling. After execution, a file called `gmon.out` will be produced containing the information about the samples collected during runtime.
- Gives data (time spent and Ts/call) by function and by line

## Instrumentation vs Instrumentation-Free

**Instrumentation**: Changes the build process such as adding extra code or changing program builds such as adding debug statements to code.
### Instrumentation Free

Don't require you to touch the source code but you may need to change how the program is built and run.
#### `time`

Built-in Linux command. 

Gives us:
- `real`: The elapsed `walltime`.
- `user`: The CPU time spent executing your programs code.
- `sys`: The CPU time spent by Sys/OS doing Disk, I/O, etc.

For a serial program: $real \approx sys + user$ but for a parallel program $user + sys \approx nprocs \times real$   

Having `sys` > `user` is a sign of inefficiency. 
#### `top`

A live dashboard of what a computer is doing. Each row is a process. 

## Memory Profiling

Use `valgrind`:

| Tool           | What it measures                               | What you learn                                                                                   |
| -------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **Massif**     | Heap memory usage over the program’s execution | How much memory the program allocates, when usage peaks, and which parts of the code allocate it |
| **Cachegrind** | Simulated CPU cache accesses and misses        | How efficiently the program accesses memory, helping explain performance problems                |
